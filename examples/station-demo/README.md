# Station demo GAMS Project

This is the local desktop-Host integration for the one-room station showcase in
[`docs/prd/0015-public-showcase.md`](../../docs/prd/0015-public-showcase.md). It
opens the authored Director rule in Code, shows the Project files, and runs a
Node Graph that compiles, binds, packs, and exports a standalone web game.

This is deliberately the **desktop Host's currently supported config shape**.
It is a local development Project, not a proposal for the future public Project
Config format.

## Local setup

The checked-in Project symlinks use Project Units from this repository. From the
repository root:

```sh
# Once for this checkout.
direnv allow

# Build the layout component and three graph plugins. The desktop Host bootstraps
# fs.comp itself before it reads gams.json.
direnv exec . make \
  build.nosync/plugins/layout.comp.wasm \
  build.nosync/plugins/lua.comp.wasm \
  build.nosync/plugins/director-compiler.comp.wasm \
  build.nosync/plugins/respack.comp.wasm

# Produce the local prebuilt browser game input. This is a developer step; the
# public walkthrough must eventually receive these files prebuilt.
direnv exec . make -C examples/station-demo/game web

# Open this Project in the existing desktop Host.
direnv exec . make APP_CWD=examples/station-demo app-run
```

`app-run` currently depends on the repository-wide plugin build target, so it
may check/build more components than this Project declares. The station Project
itself loads Layout, Lua, Director Compiler, and respack after the Host's required
filesystem bootstrap.

The initial layout uses existing UI patterns only:

- **Files** at the left;
- **Code** opened on `content/power.director`;
- **Build & Export** opened on `build.ng.json`.

If a panel was changed or restored from earlier view state, select the named
view from that panel's existing selector. Double-clicking `power.director` in
Files opens Code; double-clicking `build.ng.json` opens the Node Graph.

## Build and export in GAMS

1. In Code, keep the initial exit condition:

   ```director
   IF: PLAYER.powered
   ```

2. Save with the existing **Save** button or `Cmd+S`.
3. In **Build & Export**, press its existing **Run** toolbar button. With that
   view focused, `Cmd+Enter` invokes the same `activeView.run` action.
4. Wait for the explicit `Pipeline 'build.ng.json' completed` success toast.
   Compiler, binding, packing, missing-input, and filesystem failures throw and
   do not produce that success notification.

The graph performs this real plugin/filesystem pipeline:

1. `fs/fs::read-text` reads `content/power.director` and the fixed schema.
2. `director-compiler/director-compiler::compile` emits IR and symbol metadata.
3. `station-bindings.lua` resolves the contract's named bindings; no numeric ID
   is authored in the graph.
4. `respack/respack::build-to-file` writes only data to
   `build.nosync/station.rspk`. It does **not** regenerate `decoder.odin`.
5. `fs/fs::read-file`, `create-dir`, `write-text`, and `write-file` validate and
   copy the prebuilt `index.html`, `gl-bridge.js`, and `station-demo.wasm`, then
   write the newly generated pack last.

The standalone output is `examples/station-demo/export/web/` and contains
exactly the four runtime files expected by the game.

Serve it over ordinary static HTTP (not `file://`):

```sh
python3 -m http.server 8815 -d examples/station-demo/export/web
```

Open <http://localhost:8815>. Move with WASD/arrows, interact with E/Space, and
restart with R. In the initial export, restore power before interacting with the
exit.

## Guided rule change

In Code, change only this line in `content/power.director`:

```diff
-IF: PLAYER.powered
+IF: PLAYER.carrying_key
```

Save, run `build.ng.json` again, and reload a fresh game at
<http://localhost:8815>. The exit now requires collecting the access key. The
same prebuilt WASM consumes both packs; the Odin and decoder sources are not
regenerated by this graph.

For a local checksum check before and after a rule edit:

```sh
shasum -a 256 \
  examples/station-demo/game/build.nosync/web/station-demo.wasm \
  examples/station-demo/export/web/station-demo.wasm
shasum -a 256 examples/station-demo/export/web/station.rspk
```

The two WASM hashes must match. The pack hash changes after the prerequisite
changes. Restore `PLAYER.powered` when you want the Project back at its initial
walkthrough state. The checked-in `content/key.director` is comparison/test
evidence; `build.ng.json` intentionally compiles the editable
`content/power.director`.

## Actual local dependency inventory

Project-root symlinks:

- `plugins` -> `../../build.nosync/plugins`
- `views` -> `../../views`
- `themes` -> `../../themes`
- `ui-plugins` -> `../../ui-plugins`

Configured plugins and views:

- plugins: `layout.comp` (required by the layout UI Service), `lua.comp`,
  `director-compiler.comp`, `respack.comp`;
- primary views: `view-files`, `view-code`, `view-ng`;
- supporting internal views: `view-ng-node`, `files-rename`, `files-default`;
- theme: `themes/the98.css`.

The current desktop shell always loads the context, keys, layout, toast, popup,
and tooltip UI Services from `ui-plugins/`; only `ui-layout` has Project config.
The Host also supplies `/core/runtime.js` and serves the shared `/util`,
`/widgets`, `/css`, and `/fonts` frontend dependencies from `cmd/app/src`. The
Project-owned copy of `ng/compile-graph.lua` is the compiler that `view-ng`
actually reads.

## Verification performed

The startup regression loads the plugins declared in this Project's actual
`gams.json` and invokes the layout UI Service's initialization target through
the real runtime. This covers the previously omitted `layout.comp` dependency:

```sh
direnv exec . node examples/station-demo/tests/startup.e2e.mjs
```


The flat graph was compiled by the real `lua.comp` graph compiler and executed
through the desktop runtime with real `fs.comp`, `director-compiler.comp`, and
`respack.comp` calls. Both power and key sources produced packs that
matched their checked-in generated evidence, while the copied WASM
matched the prebuilt input byte-for-byte for both runs. The final power export
was fetched over static HTTP and matched its source files. JSON files were
parsed with `jq`.

The deeper content/runtime tests and their commands are documented in
[`content/README.md`](content/README.md); game tests are documented in
[`game/README.md`](game/README.md).

## Outstanding gaps

- `game/build.nosync/web` is still ignored developer output. A public package
  must ship the prebuilt browser files instead of asking visitors to build Odin.
- The Project Unit symlinks, generated component directory, and Host-provided
  shared frontend files require this monorepo. Released/pinned independent Units
  and the agreed public Project Config migration are not done.
- The current `make app-run` developer target builds the repository plugin set;
  a toolchain-free distributed desktop authoring bundle is not yet assembled.
- Export is not transactional because `fs.comp` has no atomic directory-replace
  operation. All inputs are validated before writes and `station.rspk` is
  written last, and any failure suppresses the success toast, but a disk failure
  can leave older files in `export/web`.
- There is no in-GAMS preview/static-server action and no browser automation.
  Serving and browser play remain the explicit manual steps above.
- Clean-machine macOS/version coverage and public subdirectory hosting remain to
  be verified for release. The game bundle itself uses relative asset URLs, but
  that release check has not been completed here.
